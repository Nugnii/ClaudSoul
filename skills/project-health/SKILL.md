# Project Health — карта здоровья проекта и план оздоровления

**Type:** orchestrator

Сначала **понимает** проект изнутри (как и почему он устроен так), затем строит карту здоровья и план починки **в правильной последовательности**. Чинит только после понимания — иначе риск сломать заложенный смысл. Ведёт по плану как трекер.

## Зачем

| Без инструмента | С инструментом |
|-----------------|----------------|
| Чиню то, что под рукой (один угол) | Сначала понимание и карта всего проекта |
| Сужу о коде, не зная ПОЧЕМУ он такой | Реконструирую замысел до оценки |
| Последовательность интуитивная → неоптимальная | Порядок выведен из рисков и зависимостей |
| Числа/находки в голове | Карта + трекер в файлах, переживают сессию |

**Корневое наблюдение (case-2026-06-20):** точечная команда без карты всего проекта неоптимальна, а починка без понимания — опасна (можно сломать смысл). Этот скилл закрывает оба разрыва.

## Фазы

```
🔍 ОХВАТ → 🧠 ПОНИМАНИЕ → 🛰️ РАЗБОР → 🗺️ КАРТА → 📐 ПЛАН → 📋 ТРЕКЕР
```

## Phase 1: ОХВАТ — определить части проекта

### Действия
1. Прочитать структуру (`ls`, дерево директорий, `CLAUDE.md`/`README` проекта).
2. Разбить проект на **части по смыслу**, не по папкам: код по подсистемам, тесты, документация, конфиги/инфраструктура, данные/знания.
3. Оценить грубый размер каждой части (файлы, строки) — чтобы знать масштаб.
4. **Определить стек(и)** по сигналам из `references/stack-rules.md` (таблица «Определение стека»): файлы-маркеры в корне или части (`pyproject.toml` → Python, `package.json`+`tsconfig.json` → TS, `go.mod` → Go и т. д.). Многостековый/monorepo — отметить стек у каждой части.

### Выход
Список частей с грубым размером и **детектированным стеком** (для каждой части / всего проекта). Если частей > 6 — сгруппировать в ≤6 кластеров.

## Phase 2: ПОНИМАНИЕ — реконструировать устройство и намерения

Прежде чем искать проблемы — понять, КАК и ПОЧЕМУ проект устроен так. Нельзя честно оценивать то, чьей логики не знаешь; чинить непонятое — значит ломать заложенный смысл.

### Действия
1. По каждой части агент-аналитик (read-only) реконструирует: архитектуру и потоки данных, точки входа, зависимости между частями, **ключевые решения и ИХ ПРИЧИНЫ** (почему так, а не иначе — из кода, комментариев, истории git, существующих правил/конвенций).
2. Особое внимание коду и правилам, которые выглядят «странно»: это часто **живая память о причине** (баг, ограничение среды, требование). Гипотеза о причине обязательна — не «это плохо».
3. Если причину не восстановить из артефактов — пометить как **«непонятое»** (не «лишнее»). Непонятое не предлагать чинить.

### Выход
Модель «как и почему работает» по каждой части — основа для разбора и плана. Часть формата вывода агента (секция `===UNDERSTANDING===`).

## Phase 3: РАЗБОР — параллельные агенты-аудиторы

### Действия
1. На каждую часть (кластер) — **отдельный агент** (Agent tool, `general-purpose`, read-only), параллельно (в одном сообщении). Каждый агент совмещает Phase 2 (понимание) и Phase 3 (находки): сначала понять, потом искать проблемы.
2. **6 категорий находок:** дублирование/рассинхрон · мёртвый код/осиротевшие файлы · файлы-монолиты (>~400 строк) · покрытие тестами · дрейф документации · скрытые риски (install-регрессия, безопасность, потеря данных).
3. Каждая проблема — с **«5 почему»** до корневой причины (см. Phase 5): фиксировать корень, не симптом.
4. Требовать: оценку здоровья N/5, размер, понимание, находки с доказательством `файл:строка`, зависимости, топ-3.

### Формат вывода агента (задать дословно)
```
===HEALTH=== N/5 + одна строка почему
===UNDERSTANDING=== как работает + ПОЧЕМУ так (ключевые решения и их причины); что осталось «непонятым»
===SIZE=== файлы | строки | тесты
===STACK=== язык/рантайм + по каким сигналам определён (pyproject/package.json/go.mod/...)
===FINDINGS=== - [категория] [P0-P3] описание — файл:строка — корень (5 почему, кратко)
===DEPENDENCIES=== зависит от … | от неё зависит …
===TOP-3=== 3 пункта по приоритету
```

### Правило
Доказательства обязательны (`файл:строка` или «заявлено X / реально Y»). Агент читает реально, не выдумывает. Есть раннер тестов — прогнать, вернуть итог.

## Phase 4: КАРТА — синтез

### Действия
1. Собрать понимание + оценки здоровья всех частей в одну таблицу.
2. Выделить **сквозные проблемы** (повторяются через части) — они важнее точечных.
3. Записать в `docs/project-health-<дата>.md`: модель «как и почему работает» (кратко), таблица здоровья, сквозные проблемы, (план — Phase 5).

### Выход
`docs/project-health-<дата>.md`. Честная общая оценка — без завышения («часть в порядке» ≠ «проект в порядке»; всегда называть охват).

## Phase 5: ПЛАН — правильная последовательность

Ядро скилла. План — не список находок, а **порядок починки** из рисков, зависимостей и корневых причин («5 почему»).

### Правила порядка (сверху вниз)
1. **Скрытые риски — первыми** (тихий вред: install-регрессия, потеря данных, безопасность).
2. **Дубли — фундамент** (один источник до наращивания).
3. **Тесты — перед рискованным рефакторингом** (характеризующий тест = страховка).
4. **Монолиты — после тестов.**
5. **Точечная чистка** (мёртвый код, висячие узлы) — в середине.
6. **Документация — последней** (числа верны только после стабилизации кода).

### Чинить корень, а не симптом
Для каждой задачи плана — корневая причина из «5 почему», а не симптом. Если корень — отсутствие механизма/правила, в план входит его установка (см. Phase 6).

### Учёт зависимостей
- Части-«листья» — изолированно. Не ломать контракты других частей. Зависимые — после тех, от кого зависят.

### Выход
Раздел «План оздоровления» в карте: фазы, для каждой — что, **почему именно здесь**, объём, затронутые части, корневая причина. Таблица зависимостей.

## Phase 6: ТРЕКЕР — вести по плану + аудит правил (канон + крафт + стек) → запись в проект + документация

### Действия
1. План → живой трекер `BACKLOG.md`: задачи по фазам, приоритет, зависимости, `Definition of Done`, статусы `☐ ◐ ☑ ⊘`. Сюда же — **conformance-беклог**: приоритизированные задачи приведения кода к универсальному крафту (F–L) и стек-паку, выявленные аудитом; каждая с корнем, объёмом и оценкой цена/выгода. **Не исполнять рефактор автоматически** — исполнение остаётся под подтверждением пользователя (см. Rules).
2. **Аудит правил против эталонов.** **MANDATORY READ:** `references/dev-rules-canon.md` (универсальные A–L: A процесс · B не-ломать · C эффективный код · D форма правил · E контекст · **F–L универсальный код-крафт** — дизайн функций, границы модулей, SOLID, DRY с оговоркой против спекуляции, именование, обработка ошибок, документация) **И** `references/stack-rules.md` (Generic-пак + пак детектированного стека). Для КАЖДОГО пункта A–L и каждого правила стек-пака проверить инстанцирование:
   - **Механизмом** (хук/страж/генератор) — лучший вид, отметить.
   - **Правилом** — отметить, уточнить под проект при необходимости.
   - **Нет** → пробел: предложить добавить, **адаптировав под проект** (не дословно из канона). Самоочевидное, что Claude и так соблюдает (канон D3) — НЕ добавлять текстом (раздувает `CLAUDE.md`). В проект писать только lean-подмножество (канон D1/D3), не весь канон; стек-специфику — lean-строки пака.
   - **Противоречит канону** → понять ПОЧЕМУ (у правила может быть причина), несогласие через вопрос, не молча переписывать.
3. **Записать недостающие правила адаптивно.** **MANDATORY READ:** `references/rules-output.md` — алгоритм выбора файла (`CLAUDE.md` vs `AGENTS.md`: правила в ОДИН авторитетный файл, второй — тонкий импорт-указатель `@AGENTS.md`; никогда не дублировать) и lean-шаблон. Наполнить авторитетный файл узким lean-ядром (команды + 2–4 универсальных из канона + lean-строки стек-пака + конвенции + квирки), адаптировав под проект (не дословно). Где правило должно срабатывать всегда — механизмом (хук/страж/CI/конфиг), не текстом (канон D5).
4. **Вести свою документацию** по ходу: документ понимания и решений (что понял, что решил, почему) — не только трекер задач. Архитектурные решения → `docs/decisions.md` (ADR).
5. Метод каждой задачи: характеризующий тест → правка → проверка → done → атомарный коммит.
6. **Цена/выгода:** не делать задачу, где унификация даёт рост кода или трогает рабочее ради косметики — `⊘ снято` с обоснованием.

### Выход
`BACKLOG.md` (трекер + conformance-беклог по F–L/стеку) + lean-правила в авторитетном файле (`AGENTS.md`/`CLAUDE.md`, адаптивно) + документация понимания/решений. Всё переживает сессию (поднимется через `SESSION.md`).

## Rules

- Скилл **не чинит** в Phase 1–5 — он понимает, строит карту и план. Починка — по трекеру (Phase 6+), с подтверждением объёма пользователем.
- **Сначала понять, потом судить и чинить.** Непонятое не трогать.
- **Уважать существующее:** код/правило, выглядящие странно, — сперва причина, потом оценка.
- Не завышать: «готово/в порядке» — только с явным охватом.
- Большой проект → агенты параллельно (Phase 3).
- План показывать с цифрами; решение «идти по нему» — за пользователем.
- Запись правил в проект — **lean** (канон D1/D3): не копировать канон/паки дословно; conformance-рефактор по F–L/стеку **не исполнять без подтверждения** пользователя (как и любую починку).

## Definition of Done

- [ ] Phase 1: проект разбит на части с грубым размером; **определён стек(и)** по файлам-маркерам (`references/stack-rules.md`)
- [ ] Phase 2: для каждой части реконструировано «как и ПОЧЕМУ работает»; «непонятое» помечено
- [ ] Phase 3: каждая часть разобрана агентом; находки с доказательствами и корнем («5 почему»)
- [ ] Phase 4: карта (понимание + здоровье + сквозные проблемы) в `docs/project-health-<дата>.md`
- [ ] Phase 5: план с последовательностью, зависимостями и корневыми причинами записан туда же
- [ ] Phase 6: `BACKLOG.md` (+ conformance-беклог по F–L/стеку, рефактор не исполнен без подтверждения); **аудит против канона A–L** (`references/dev-rules-canon.md`) **и стек-пака** (`references/stack-rules.md`) — каждый пункт сверен, пробелы дополнены адаптированно
- [ ] Phase 6: lean-правила записаны в авторитетный файл (`AGENTS.md`/`CLAUDE.md`, адаптивно по `references/rules-output.md`; второй — тонкий импорт-указатель, без дублирования); ведётся документация решений (`docs/decisions.md`)
- [ ] Карта и план показаны пользователю; решение о починке — за ним
