# Адаптивная запись правил в проект — куда и как

> Применяется в Phase 6, когда аудит выявил пробелы и нужно дописать правила. Цель —
> положить правила в ОДИН авторитетный файл, второй (если есть) сделать тонким
> указателем, и писать **lean** (канон D1: каждая строка обязана менять поведение
> агента, иначе убрать). Что выводится из кода/конфигов и самоочевидно (D3) — не
> писать; что должно срабатывать всегда (D5) — делать механизмом, не текстом.

## Факт корректности: CLAUDE.md vs AGENTS.md

Claude Code НАТИВНО авто-загружает только `CLAUDE.md`. `AGENTS.md` — кросс-вендорный
стандарт (Cursor / Copilot / Codex), но сам Claude Code его автоматически НЕ читает.
Мост — нативная директива импорта: строка `@AGENTS.md` внутри `CLAUDE.md` механически
инжектит содержимое `AGENTS.md` в контекст при старте сессии (это МЕХАНИЗМ, канон D5, а
не прозовый совет «прочитай файл»). Поэтому при создании с нуля авторитетным делаем
`AGENTS.md` (портируемый), а `CLAUDE.md` — одностроковый импорт-указатель на него.

**ИНВАРИАНТ:** правила живут ровно в ОДНОМ авторитетном файле. Второй (если есть) —
только тонкий указатель на первый. Никогда не дублировать правила в обоих — расхождение
даёт ложную модель (как README↔CLAUDE в global docs-правиле). Один источник истины на
проект — как `VERSION` в versioning discipline.

## Алгоритм выбора файла

1. **Детект файлов правил в корне:** `CLAUDE.md`, `AGENTS.md` (а также
   `.cursorrules`, `.github/copilot-instructions.md` — учесть как сигнал
   существующих правил, но не как цель записи).
2. **Ветвление по тому, что найдено:**
   - **(a) Только `CLAUDE.md`** → писать в него (авторитетный = CLAUDE.md). AGENTS.md
     не создавать (портируемость не просили).
   - **(b) Только `AGENTS.md`** → писать в него (авторитетный = AGENTS.md). Создать
     тонкий `CLAUDE.md` из одной строки `@AGENTS.md` (нативный импорт) — Claude Code
     механически подхватит правила через него.
   - **(c) Оба** → определить авторитетный (где реально лежат правила); предпочесть
     авторитетным `AGENTS.md` — тогда мост `@AGENTS.md` работает напрямую. Правила в
     обоих — это уже дрейф: озвучить наблюдением (B5) и предложить свести в один.
     Второй привести к тонкому импорт-указателю. Третий файл не плодить.
   - **(d) Нет ни одного** → дефолт: `AGENTS.md` (портируемый, авторитетный) + тонкий
     `CLAUDE.md` из строки `@AGENTS.md`. Правила переносимы между вендорами И механически
     авто-загружаются в Claude Code. Второй файл — одна строка импорта, не дубль правил,
     поэтому это не over-engineering. Если проект заведомо одно-инструментный (только
     Claude Code, портируемость не нужна) — допустим один `CLAUDE.md` без `AGENTS.md`
     (канон C1: не плодить впрок); выбор по контексту, дефолт — портируемая пара.
3. **Наполнить авторитетный файл** по шаблону ниже. Соблюдать канон: D1 (коротко),
   D3 (не вносить выводимое из кода и стандартные конвенции — для них достаточно
   конфигов из Generic-пака G3), D5 (где правило должно срабатывать ВСЕГДА — ставить
   механизмом: хук/CI/конфиг, а не строкой). Generic-пак и stack-пак дают КАНДИДАТОВ —
   вносить только не покрытое механизмом и не самоочевидное.
4. **Тонкий указатель** (для случаев b/d и неавторитетного файла в c) — нативный
   импорт, не проза, без дублирования правил. Содержимое `CLAUDE.md` целиком:
   ```
   @AGENTS.md
   ```
   Это директива импорта Claude Code (МЕХАНИЗМ, канон D5): инжектит `AGENTS.md` в
   контекст при старте. Прозовое «правила в AGENTS.md, читай его» — НЕ использовать
   (совет дрейфует, зависит от того, послушает ли модель). Обратное направление
   (авторитетный `CLAUDE.md` + портируемый `AGENTS.md`) импортом не покрывается —
   потребует дублирования/синка; поэтому авторитетным предпочитать `AGENTS.md`.

## Правила размещения

- **Один авторитетный файл, второй — указатель.** Никакого дублирования правил.
- **Механизм > текст (D5).** Должно срабатывать всегда без исключений → хук/CI/конфиг,
  не текстовое правило (совет дрейфует).
- **Lean (D1/D3).** Каждая строка меняет поведение агента, иначе убрать. Выводимое из
  кода, стандартные конвенции языка, самоочевидное («пиши чистый код») — не писать.
- **Адаптировать, не копировать.** Канон A–L и стек-паки — эталон для сверки; в проект
  идёт узкое lean-ядро, переформулированное под проект, не дословный текст канона.

## Итог: что записать

- Авторитетный файл наполнен lean-ядром (команды + 2–4 универсальных + stack-lean +
  конвенции + квирки). Второй файл — тонкий указатель или отсутствует.
- Пробелы, которые должны срабатывать всегда, — отправлены в механизм (хук/CI/конфиг),
  отмечены в BACKLOG как задача установки механизма, а не как текстовая строка.
- Ничего из канона/паков не скопировано дословно — всё переформулировано под проект.
