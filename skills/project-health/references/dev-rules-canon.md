# Канон правил разработки с Claude — эталон для аудита

> Универсальные лучшие практики организации разработки с Claude. Это **эталон**,
> с которым `/project-health` (фаза «Аудит правил») сравнивает правила проекта и
> дополняет пробелы. НЕ копировать дословно в проект — проверять, есть ли в
> проекте инстанцирование каждого пункта (правилом ИЛИ механизмом), и заполнять
> недостающее, адаптируя под проект.
>
> Источник: Anthropic «Best practices for Claude Code»
> (https://code.claude.com/docs/en/best-practices) + общепринятая инженерия.
> Принцип над всеми: где правило можно сделать механизмом (хук/страж/генератор) —
> делать механизмом; текст — для того, что нельзя автоматизировать.

## A. Рабочий процесс

- **A1. Explore → Plan → Code → Commit.** Сначала исследовать и спланировать,
  потом кодить — иначе решается не та задача. План обязателен для многофайлового /
  незнакомого / неопределённого; пропускать, если диф описывается одним предложением.
- **A2. Дать Claude способ проверить работу.** Тест / сборка / линтер / скриншот —
  что-то, что возвращает pass/fail. Показывать **доказательство** (вывод теста,
  команду и её результат), а не утверждать «готово».
- **A3. TDD где уместно.** Тесты из пар вход/выход → потом код, итерировать до зелёного.
- **A4. Корневая причина, не симптом.** Не подавлять ошибку — устранять причину.
- **A5. Course-correct рано.** Поправлять, как только заметил отклонение. После 2
  неудачных коррекций подряд — сбросить контекст и начать с лучшим промптом.
- **A6. Адверсариальный ревью.** Перед «готово» — независимая проверка дифа в свежем
  контексте (субагент видит только диф + критерии). Флагировать только пробелы
  корректности/требований, не стиль (иначе over-engineering).

## B. Не ломать существующее

- **B1. Следовать существующим паттернам.** Найти пример в кодовой базе, повторить
  его стиль/структуру, а не навязывать свой.
- **B2. Не плодить зависимости.** Строить на уже используемых библиотеках; новую
  зависимость — только при явной необходимости.
- **B3. Регрессионная страховка.** Рефактор без теста опасен. Для монолита без теста
  — сперва характеризующий тест (сквозной прогон), потом правка.
- **B4. Воспроизвести багом-тестом.** Падающий тест на баг → потом фикс.
- **B5. Хирургические правки.** Только под запрошенную задачу; не рефакторить и не
  «подчищать» соседнее без запроса. Замеченное проблемное — озвучить наблюдением.

## C. Эффективный код (без переусложнения)

- **C1. Без over-engineering.** Лишние слои абстракции, defensive-код, тесты
  невозможных случаев — вред. Минимум, решающий задачу.
- **C2. Без спекулятивных фич.** Не просили — не добавляй; нужна — спроси отдельно.
- **C3. Прагматичная производительность.** Не преждевременная оптимизация; где можно
  — единичный тест вместо всего набора, дешёвая проверка вместо дорогой.

## D. Правила проекта (CLAUDE.md) и их форма

- **D1. Коротко.** На каждую строку: «убрать эту строку → Claude начнёт ошибаться?
  Нет → убрать». Раздутый CLAUDE.md → Claude теряет важные правила в шуме.
- **D2. Включать:** команды, которые не угадать; стиль, отличный от дефолта;
  тест-инструкции; этикет репозитория; архитектурные решения проекта; квирки среды;
  неочевидные гочи.
- **D3. Исключать:** выводимое из кода; стандартные конвенции языка; самоочевидное
  («пиши чистый код»); детальные API-доки (ссылкой); часто меняющееся.
- **D4. Подрезать регулярно.** Если правило не меняет поведение — удалить или
  превратить в хук.
- **D5. Механизм > текст.** Правило, которое должно срабатывать всегда без исключений
  — хук/страж (детерминизм), а не текстовое правило (совет).

## E. Контекст и сессии

- **E1. Управлять контекстом.** Сброс между несвязанными задачами; субагенты для
  исследования (отдельный контекст, возвращают сводку); не давать контексту
  засоряться неважным.

## F. Дизайн функций

> Секции F–L — **универсальный код-крафт** (организация самого кода), дополняют A–E
> (организацию процесса). При аудите проверяются так же: правилом ИЛИ механизмом,
> пробел дополнять адаптированно. В проект пишется только **lean-подмножество**
> (см. `references/stack-rules.md` → lean-ядро), не вся секция — F–L это эталон для
> сверки, не текст для копирования. Все F–L — нормы для НОВОГО/правимого по задаче
> кода, не мандат на сплошной рефактор: B5 (хирургичность) выше — замеченное
> несоответствие озвучить наблюдением и внести в BACKLOG с оценкой цена/выгода
> (Phase 6), не править молча.

- **F1. Имя раскрывает намерение.** Имя отвечает «что/зачем», не «как». Длинное
  ясное > короткое загадочное; нужен комментарий к имени → имя плохое. Булевы —
  утверждение (`isReady`, `hasAccess`). Глагол для функции, существительное для
  значения. Один смысл — одно слово во всём проекте (не `fetch`/`get`/`load`
  вперемешку). LLM тяготеет к generic (`handleData`, `utils`, `process`).
- **F2. Функция делает одно.** Один уровень абстракции, одна причина измениться.
  Нарушение: имя содержит «и»/«затем»; тело мешает оркестрацию с низкоуровневыми
  деталями; не описать одной фразой. Команда (меняет состояние) и запрос (возвращает
  значение) разделены (CQS).
- **F3. Мало аргументов.** 0–2 — норма, 3 — предел, 4+ — сигнал группировать в
  объект/структуру. Булев-флаг, переключающий поведение, → две функции. Избегать
  выходных-параметров (мутация аргумента ради возврата) — возвращать значение.
- **F4. Без скрытых побочных эффектов.** Функция делает то, что обещает имя, и ничего
  сверх: никаких тихих правок глобального состояния, неожиданной инициализации,
  записей в БД/файл из функции с «читающим» именем. Эффект — в имени или вынесен.
- **F5. Ранний возврат вместо вложенности.** Guard-clause на невалидный/краевой
  случай в начале → плоское тело. Глубина > 2–3 — сигнал извлечь функцию. Не `else`
  после `return`.

## G. Границы модулей

- **G1. Высокая связность (cohesion).** В одном модуле — то, что меняется по одной
  причине и работает с одними данными. Трогают по несвязанным причинам (UI И расчёт
  И формат) → разбить. Имя модуля — единая ответственность, не `misc`/`common`/
  `utils`-свалка.
- **G2. Слабая связанность (coupling).** Модуль зависит от минимума чужих деталей;
  общение через узкий явный интерфейс, не через внутренности соседа. Не лезть в
  приватные поля/глубокие пути (Law of Demeter: `a.b.c.d` — запах). Уже Public B1.
- **G3. Направление зависимостей — внутрь.** Детали (I/O, БД, сеть, фреймворк, UI)
  зависят от политики (домен), не наоборот. Доменная логика не импортирует
  инфраструктуру; граница — через интерфейс/порт, реализация инжектится. Циклов между
  модулями нет. Самая частая структурная ошибка LLM — SQL/HTTP/env прямо в доменной
  функции; дорого расцеплять задним числом.
- **G4. Скрывать реализацию за интерфейсом.** Публичный контракт стабилен и минимален;
  внутреннее устройство (структуры, алгоритм, библиотека) скрыто и заменяемо без
  затрагивания вызывающих. Не экспортировать то, что не обязано быть публичным
  (information hiding, Parnas).

## H. SOLID (стек-агностично)

- **H1. Одна причина измениться (SRP).** Модуль/класс/функция отвечает перед одной
  группой заинтересованных. Смешение причин изменения (бизнес-правило + представление
  + хранение в одном месте) — разделить. Корень G1 и тестируемости.
- **H2. Открыт для расширения, закрыт для правки (OCP) — в меру.** Новое поведение
  добавлять, не переписывая отлаженное ядро — через полиморфизм/стратегию/плагин ТАМ,
  где вариативность **уже доказана**. НЕ строить точки расширения впрок:
  преждевременный OCP = спекулятивная абстракция (C2). OCP подчинён C1/C2.
- **H3. Подтип честно заменяет базу (LSP).** Реализация интерфейса не нарушает
  контракт базы: не ужесточает предусловия, не ослабляет постусловия, не бросает
  неожиданных ошибок, не требует проверок типа у вызывающего. «Не совсем» подходит —
  иерархия неверна (`if isinstance(...)` у клиента — симптом).
- **H4. Узкие интерфейсы (ISP).** Клиент не зависит от методов, которыми не
  пользуется. Несколько маленьких ролевых интерфейсов > одного «жирного». Реализация,
  вынужденная делать заглушки на половину методов, — сигнал расщепить.
- **H5. Зависеть от абстракций (DIP).** Политика и деталь обе зависят от абстракции;
  абстракция не зависит от детали. Зависимости передавать извне (инъекция), не
  создавать жёстко внутри (`new`/прямой импорт конкретики в ядре). Операционализирует
  G3 и делает ядро тестируемым подменой.

## I. DRY и переиспользование (с оговоркой против спекуляции)

> Главное напряжение канона: **C1 (без over-engineering) и C2 (без спекулятивных
> фич) ВЫШЕ DRY.** DRY применяется только к доказанному дублированию ЗНАНИЯ (I1) и
> только после третьего повтора (I2). I4/H2 запрещают строить абстракции/точки
> расширения впрок. DRY никогда не оправдывает преждевременную абстракцию — наоборот,
> ограничивает её.

- **I1. DRY к знанию, не к тексту.** Один кусок ДОМЕННОГО знания (правило, формула,
  константа, схема) — в одном авторитетном месте, остальное ссылается. Два фрагмента,
  совпавших случайно и меняющихся по разным причинам, — НЕ дублирование; объединение
  свяжет несвязанное (правка одного сломает другое).
- **I2. Правило трёх перед абстракцией.** Извлекать общее после третьего повтора, не
  первого/второго. До этого — терпеть дубль. Переделать неверную абстракцию тяжелее,
  чем устранить дубль, когда форма ясна (AHA: «avoid hasty abstractions»; дублирование
  дешевле неверной абстракции). Прямой механизм против C2 внутри DRY.
- **I3. Сначала искать существующее.** Перед новой утилитой/хелпером — поискать, нет
  ли уже такого в кодовой базе (B1) или в используемой зависимости (B2).
  Переиспользовать/расширить, не плодить параллельную реализацию (дубль-через-незнание
  — частый источник рассинхрона).
- **I4. Не over-DRY.** Если устранение дубля рождает связанность, непрозрачные
  флаги-параметры, обратные зависимости или код длиннее/непонятнее исходного —
  оставить дубль. Читаемость и развязка важнее счётчика строк (прямая ссылка на C1 и
  Phase 6 цена/выгода). DRY — средство, не цель.

## J. Именование и консистентность

> J — специализация B1 на словарь имён и структуру файлов (не дубль): B1 про
> повторение стиля кода в целом, J — конкретно про нейминг, словарь домена и
> согласованность. Если в проекте уже есть сильное B1-правило — J считать
> инстанцированным, не добавлять текстом (D3).

- **J1. Следовать конвенции проекта, не своей.** Casing (camelCase/snake_case),
  структура папок, паттерны файлов — как уже принято, даже если личное предпочтение
  иное. Новый файл выглядит как сосед. Нет конвенции — доминирующая в стеке/языке.
  Консистентность важнее «правильности» отдельного выбора.
- **J2. Единый словарь домена.** Одно понятие — одно имя во всём коде (не
  `user`/`account`/`member` для одной сущности). Имена кода = язык предметной области
  (ubiquitous language). Антонимы согласованы (`open`/`close`, не `open`/`stop`).
- **J3. Без шумовых и кодированных имён.** Без венгерской нотации, типовых префиксов,
  `Manager`/`Data`/`Info`/`Object`-наполнителей, номерных суффиксов (`a1`, `a2`). Имя
  различает по смыслу, не по типу. Магические числа — именованными константами.

## K. Обработка ошибок

> K — это A4 (корневая причина, не симптом), перенесённый с фазы отладки на фазу
> написания: A4 «чини причину»; K «не создавай условий, где причина прячется»
> (проглоченный catch, дефолт вместо ошибки). Дополняют, не конфликтуют.

- **K1. Падать рано (fail fast).** Невалидный вход / нарушенный инвариант → ошибка
  немедленно в точке обнаружения, не «протащить» дальше. Валидировать на границе
  модуля; внутри ядра данные считать валидными. Не возвращать null/дефолт, скрывая
  нарушение.
- **K2. Не глотать ошибку.** Никаких пустых/«проглатывающих» catch, `except: pass`,
  лог-и-молча-продолжай при сломанном инварианте. Поймал — обработать осмысленно
  (восстановить, обогатить контекстом и пробросить, или явно деградировать).
  Подавление ≠ обработка. LLM часто пишет «безопасный» catch, прячущий баг.
- **K3. Осмысленные сообщения.** Текст ошибки несёт: что, где, с какими данными, по
  возможности — что делать. Не `Error`/`Invalid`/`Something went wrong`. Сохранять
  причинную цепочку (wrap/cause), не терять исходный стектрейс — она ведёт к корню (A4).
- **K4. Ошибки — часть контракта.** Отделять ожидаемые сбои (нет файла, отказ сети,
  невалидный ввод — обработать) от багов программиста (нарушенный инвариант — упасть
  громко). Не использовать исключения для нормального потока. Освобождать ресурсы
  детерминированно (`finally`/`with`/`defer`).

## L. Документация и стандарты записи

> L1 = F6-уровень того же правила: «почему»-комментарий и есть носитель причины, об
> утрате которой предупреждает B5 («странное = живая память»). Укрепляют друг друга.

- **L1. Комментарий — ПОЧЕМУ, не ЧТО.** Код выражает ЧТО; комментарий — только
  неочевидное ПОЧЕМУ: причина решения, обход бага, ссылка на требование/тикет,
  странность среды, осознанный неинтуитивный выбор. Не пересказывать код. Закоммен-
  тированный код — удалять (git помнит). Комментарии-«что» устаревают и лгут.
- **L2. Документировать по ходу (doc-as-you-go).** Публичный контракт (API, формат
  данных, точка входа) документируется вместе с кодом, не «потом». README отвечает:
  что это, как запустить, как тестировать, как внести вклад. Документация рядом с
  кодом, обновляется в том же коммите (см. docs-family-check).
- **L3. ADR для значимых решений.** Решение с последствиями (выбор стека, граница,
  паттерн, важный trade-off) фиксировать кратко: контекст → решение → причина →
  последствия. В момент решения, append-лог, не задним числом (`docs/decisions.md`).
- **L4. Changelog и явная версия.** Изменения, видимые снаружи, — в CHANGELOG (Keep a
  Changelog, блок Unreleased); один источник версии. На языке эффекта для
  пользователя, не коммитов. Уже Versioning discipline; здесь — как код-норма для
  аудита незнакомого проекта.
- **L5. Самодокументируемость прежде комментариев.** Прежде чем писать комментарий-
  объяснение — сделать код понятным сам: переименовать, извлечь функцию с говорящим
  именем, ввести именованную промежуточную переменную. Комментарий — когда ясность
  кодом недостижима. Лучший комментарий — тот, что не понадобился.

## Lean-подмножество для записи в проект

F–L — **эталон для сверки**, не текст для CLAUDE.md. В проект пишется только узкое
lean-ядро (F1/F2/F5 · G3 · H5 · I1/I2 · K1/K2 — то, что LLM нарушает чаще всего и что
не покрыто механизмом). Стек-специфика — отдельно (`references/stack-rules.md`).
Самоочевидное, что Claude и так соблюдает (D3), и выводимое из конфигов (форматтер,
линтер) — НЕ писать текстом. Адаптивный выбор файла и шаблон — `references/rules-output.md`.

## Как пользоваться при аудите

Для КАЖДОГО пункта A–L (и каждого правила стек-пака — `references/stack-rules.md`): есть ли в проекте его инстанцирование?
- **Да, правилом** — отметить, при необходимости уточнить под проект.
- **Да, механизмом** (хук/страж/генератор) — лучший вид, отметить.
- **Нет** — пробел: предложить добавить, адаптировав под проект (не дословно из
  канона). Если пункт самоочевиден и Claude его и так соблюдает (D3) — НЕ добавлять
  текстом, это раздует CLAUDE.md.
- **Существующее правило противоречит канону** — понять ПОЧЕМУ (у него может быть
  причина), несогласие через вопрос, не молча переписывать.
