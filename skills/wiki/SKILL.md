# Wiki — нарративный рендер сущности

**Type:** worker

Делает то, что `/entity` не делает: берёт сущность, её атрибуты и связи и превращает в читаемую wiki-страницу с ссылками на соседей по графу. Разметка зависит от `entity_type` — у компании нет «даты рождения», у концепции нет «адреса», у персонажа свои разделы.

**Не** редактирует файлы. Только чтение + рендер.

## Step 1: Получить данные сущности

Определить путь к движку (как в `/entity`, `/ingest`):

```bash
# Резолвер репо — общий ~/.claude/bin/resolve-claudsoul-repo.sh (вынесен из inline-копий, ставит install.sh).
source "$HOME/.claude/bin/resolve-claudsoul-repo.sh" 2>/dev/null \
    || { echo "ERROR: нет ~/.claude/bin/resolve-claudsoul-repo.sh — запусти install.sh из корня ClaudSoul" >&2; exit 1; }
REPO=$(resolve_claudsoul_repo) || exit 1
PY="$REPO/mcp-server/.venv/bin/python"
ENTITY_DIR="$HOME/.claude/global-lessons"

"$PY" -m ingest.cli show-entity "<query>" > /tmp/wiki-entity.json
```

Ambiguous → показать список, остановиться. Not_found → предложить `/ingest`.

## Step 2: Подтянуть соседей (для ссылок с названиями)

Для каждого entity-файла в `related_relations` и `edges` сделать быстрый `show-entity` по slug'у (убрать `entity-` и `.md`). Так у ссылок будут живые имена, а не голые slug'и. Пропускать при `not_found` (связь битая — просто не ссылаться).

Параллельно — не подряд. Это read-only, можно батчем через `xargs -P`.

## Step 3: Выбрать шаблон по entity_type

Каждый тип — свой набор разделов. Разделы пустые (нет данных) не выводить.

### person
- **Заголовок:** `# [name]`
- **Подзаголовок** (одна строка): роль + основная аффилиация из `works_at` исходящей связи
- **Кто это.** Description + ключевые атрибуты в связном тексте.
- **Где работает / работал.** `works_at` → список с ссылками
- **Чем известен.** `created`, `participated_in` → что создал / в чём участвовал
- **Связи.** `knows` → люди
- **Учился.** `studied_at` → образование
- **Упоминания в прессе.** Входящие `mentions` от `entity_type: work` с `tags: [publication]`. Формат см. Step 7.
- **Источники.** Список `source_id` из атрибутов (дедуплицировать).

### company
- **Заголовок:** `# [name]`
- **Подзаголовок:** одна строка — description.
- **Что делает.** Развёрнутый абзац на основе description + ключевых атрибутов (target_audience, client_count, years_operating и т.п.).
- **Реквизиты.** `legal_name`, `legal_form`, `nip`/`tax_id`, `address` или `city` + `country`. В одну-две строки через ` · `.
- **Контакты.** `website`, `email`, `phone*`, `telegram`, `office_hours`. Одной строкой через ` · `.
- **Руководство / люди.** Входящие `works_at` (от персон). Формат: `[Имя](ссылка) — <должность>`. Должность берётся в порядке: `relation.description` (очищенная от имени компании) → `entity.attributes.role` → если ни одного нет, не выводить строку вообще. **НИКОГДА не выводить тип связи (`works_at`, `part_of`) как «должность»** — это технический маркер графа, а не факт о человеке.
- **Услуги / тарифы.** Атрибуты с ценами (`*_fee`, `monthly_fee`, `price*`), расшифровка в связный список.
- **Как оформляет клиентов.** Если входящие `applied_to` содержат несколько типов контрактов (UoD, UZ, B2B и т.п.) — формулировать как «клиент может оформляться через A, B или одновременно через несколько», НЕ «по одному из двух». Разные контракты не взаимоисключающие по умолчанию — только если в relation.description явно сказано «вместо» / «либо-либо».
- **Инфраструктура.** Входящие `applied_to` от products/companies типа `tool` / `bank` / `SaaS`.
- **Как работает.** Входящие `applied_to` от concepts правового/налогового характера — что компания «применяет».
- **Альтернативы / Конкуренты.** `similar_to` связи.
- **Упоминания в прессе.** Входящие `mentions` от `entity_type: work` с `tags: [publication]`. Формат см. Step 7. Если пусто — пропустить раздел (в отчёте `/enrich` публикации увидит только по запуску). Сортировка: по дате убыванию.
- **Источники.**

### concept
- **Заголовок:** `# [name]` + alias'ы в круглых скобках
- **Определение.** Description как первый абзац.
- **Ключевые параметры.** Таблица/список атрибутов (value + единица измерения если понятно из key, например `rate`, `threshold`).
- **Где применяется.** Исходящие `applied_to` → к чему применяется.
- **Что применяется к нему.** Входящие `applied_to` → что его использует/регулирует.
- **Альтернативы.** `similar_to`.
- **Противоречит.** `contradicts` — и почему (берём из relation.description).
- **Юрисдикция / контекст.** Если есть `applied_to` на place — вынести отдельной строкой.
- **Источники.**

### product
- **Заголовок:** `# [name]`
- **Подзаголовок:** одна строка description.
- **Описание.** Развёрнутый абзац.
- **Характеристики.** Атрибуты (has_api, license, vendor и т.п.).
- **Кто использует.** Исходящие `applied_to` к компаниям.
- **Альтернативы.** `similar_to`.
- **Источники.**

### place
- **Заголовок:** `# [name]` + aliases
- **Описание.** Description.
- **Географический контекст.** `part_of` (входит в…) + входящие `part_of` (что в нём).
- **Что применимо в этой юрисдикции.** Входящие `applied_to` (концепции, правовые нормы, продукты, привязанные к месту).
- **Организации здесь.** Входящие `part_of` от company.
- **Источники.**

### event
- **Заголовок:** `# [name]`
- **Когда.** `valid_from` или атрибут `date`.
- **Что произошло.** Description + атрибуты.
- **Участники.** Входящие `participated_in`.
- **Последствия.** `caused_by` / `led_to`.
- **Источники.**

### work
- **Заголовок:** `# [name]`
- **Авторы.** Входящие `created` (от person/company).
- **О работе.** Description + атрибуты.
- **Связанные концепции.** `applied_to` исходящие.
- **Похожие работы.** `similar_to`.
- **Источники.**

## Step 4: Формат ссылок

**Ссылки на сущности:**
- Каждая упомянутая сущность — markdown-ссылка на её .md файл: `[отображаемое имя](/абсолютный/путь/к/entity-slug.md)`.
- Отображаемое имя = `name` ИЛИ `aliases[0]` — выбрать **одно** целиком. Никогда не смешивать алфавиты внутри одного имени (не «Бerseneu Kanstantsin»). Для юрлиц/физлиц по умолчанию — `name` (канонично из официального источника). Алиас — если уместен контекст (русскоязычная аудитория и есть русская форма).
- Путь вычислять как `$HOME/.claude/global-lessons/entity-<slug>.md` — но `$HOME` раскрыть в абсолютный. Это критично, иначе VSCode не откроет.
- Если в тексте сущность появляется несколько раз — ссылку только на первое упоминание, дальше просто имя.

**Ссылки на контакты (атрибуты company/person):**
- `telegram: @handle` → `[@handle](https://t.me/handle)` (убрать `@` из URL, оставить в тексте)
- `website: https://...` или `domain.tld` → `[домен](https://full-url)` (добавить `https://` если схемы нет)
- `email: x@y.z` → `[x@y.z](mailto:x@y.z)`
- `phone*`: нормализовать к `+CC...` → `[+48 ...](tel:+48...)` (пробелы в тексте оставить, в `tel:` убрать)
- Ссылка **всегда** кликабельная. Голый `@handle` или `info@...` в тексте wiki — баг.

## Step 4b: Контрадикции — показывать, не прятать

Если у атрибута есть поле `contradiction: {stated_value, stated_source, stated_confidence}` — это живой конфликт между источниками. Wiki обязана его показать, а не выводить только «победившее» значение.

**Формат inline** (для атрибутов в связном тексте или через ` · `):

```
<value> ⚠ (альт. «<stated_value>» из <stated_source_slug>)
```

Примеры:
- Адрес: `ul. Przykładowa 1/100, 00-001 Warszawa ⚠ (альт. «00-002 Warszawa» из example-co-обзор-2026-04-21)`
- Часы: `10:00–18:00 по будням ⚠ (альт. «10:00–17:00» из example-co-обзор-2026-04-21)`

**Правила:**
- `⚠` — обязательный маркер. Без него читатель не заметит конфликт.
- `stated_source` — сокращать до первого сегмента слага (до второго `-` если длинно), но **не** опускать совсем: читатель должен понимать откуда альт-значение.
- Если контрадикций на одном атрибуте несколько (schema v0.2 хранит одну — но на будущее) — показать все через `; альт. ...`.
- В раздел «Источники» источник контрадикции тоже включить (чтобы читатель мог провалиться).
- **Никогда не замалчивать** контрадикцию. Даже если `stated_confidence` низкий — факт расхождения есть, и это важнее «красоты» карточки.

**В разделе «Реквизиты» / «Контакты»** — контрадикция идёт inline в той же строке через ` · `, не переносить на новую.

**В таблицах / списках параметров** (concept → «Ключевые параметры») — контрадикция идёт в той же ячейке, маркер `⚠` и альт-значение в скобках.

## Step 5: Раздел «Источники»

Собрать уникальные `source_id` из всех атрибутов (до знака `:`) + из `related_facts[].sources` + из `related_relations[]` source list (если есть). Показать как список:

```
**Источники:** example-co-обзор-2026-04-21
```

Если источник один — одной строкой. Если несколько — маркированный список.

## Step 7: Упоминания в прессе (publications)

Когда у сущности есть входящие `mentions` от сущностей с `entity_type: work` и `tags` содержит `publication`:

**Источник имени издания:** `show-entity` каждого work → взять его исходящую `published_in` → загрузить media-сущность → её `name` = «publisher» (starting v0.4.0, attribute `publisher` на work больше не используется). Ссылка на имя — на entity-файл медиа (чтобы можно было провалиться).

**Формат одной записи:**

```
- [<media_name>](<абс.путь к entity-media.md>) · <YYYY-MM-DD> · [<title>](<url>)  
  <excerpt> — <author_name> (<language>) · <editorial|ad_partnership>
```

Пример:
```
- [example-it.media](~/.claude/global-lessons/entity-example-it.media.md) · 2024-12-02 · [Как сэкономить на налогах в Польше](https://example-it.io/news/...)  
  «Записаться на бесплатную консультацию с компанией ProjectA можно по ссылке…» — Team Adviser (ru) · ad_partnership
```

**Правила:**
- Сортировка: по `published_at` убыванию (новое сверху)
- Источник имени издания — name media-сущности (не домен из URL, не вычисление из slug). Если `published_in` отсутствует у work — fallback на `host` из url + warning в отчёт (это баг интеграции, на v0.4+ каждая публикация должна иметь media).
- Тип контента: по тегу work — `tags: [... ad_partnership]` → «ad_partnership», иначе → «editorial». Это важный сигнал читателю: редакция или спонсор.
- Если `author_name` отсутствует — опустить «— <author>» часть
- Если `language` = язык самой компании (например `ru` для русскоязычной аудитории) — можно опустить маркер языка
- Максимум 10 публикаций в wiki (если больше — показать самые свежие 10 + строка `... ещё N публикаций, см. /entity <slug> для полного списка`)
- Если публикации мультиязычные — группировать по языку с подзаголовками `**Русскоязычная пресса:**`, `**Польская пресса:**`, `**English media:**`

## Step 6: Подвал

Одной строкой после источников:

```
_Сущность (company, confidence 2/5, 17 связей). Полная карточка: /entity projecta_
```

Это позволяет провалиться в raw-frontmatter при необходимости.

## Rules

- Нарратив > перечисление. Атрибуты переплести в текст там, где это читается естественно. Сухой dump оставить для `/entity`.
- Не выдумывать данные. Если раздела не на что опереться — пропустить.
- Не сокращать адрес / NIP / контакты — это ключевая информация.
- `applied_to` направление важно: `X applied_to Y` = «X применяется к Y». В разделе Y: `X применимо к нам`. В разделе X: `применяется в Y`.
- Одна сущность — одна wiki-страница. Не рендерить за один запуск несколько.
- Если все разделы пусты кроме заголовка — честно скажи «Минимальная запись, наполнение через /ingest».

- [ ] Источники собраны и дедуплицированы

- [ ] Подвал с `/entity` подсказкой на месте
