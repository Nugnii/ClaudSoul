# Шаблоны артефактов декомпозиции (spec → plan → tasks)

> Используются скиллом /decompose для задач 8+ шагов.
> Происхождение: адаптация Spec-Driven Development (github/spec-kit) под ClaudSoul.
> Принцип: спецификация — источник истины. Изменилась спека → план и tasks регенерируются вниз, не правятся руками.

## Размещение

```
<корень проекта>/.claude-docs/specs/<YYYY-MM-DD>-<slug>/
├── spec.md    # ЧТО и ЗАЧЕМ — требования, без технических решений
├── plan.md    # КАК — шаги, зависимости, gates
└── tasks.md   # Исполняемые задачи со статусами
```

`<slug>` — короткое kebab-case имя задачи (латиницей).

## spec.md

```markdown
# Spec: [название задачи]

**Дата:** YYYY-MM-DD · **Статус:** draft | clarified | approved

## Demand
- **Кому нужно:** [кто потребитель результата]
- **Какая потребность:** [боль/цель — почему вообще делаем]
- **Успех:** [проверяемый критерий — что будет считаться сделанным]

## Требования
<!-- Только ЧТО и ЗАЧЕМ. Никаких технологий, файлов, архитектуры — это plan.md -->
1. [требование — проверяемое и однозначное]
2. [требование]
3. [NEEDS CLARIFICATION: конкретный вопрос пользователю]

## Не входит
- [явно исключённое из scope]

## Чеклист готовности спеки
- [ ] Нет маркеров [NEEDS CLARIFICATION]
- [ ] Каждое требование проверяемо (можно ответить «сделано/не сделано»)
- [ ] Критерий успеха измерим
- [ ] «Не входит» заполнено (пустой раздел = scope не зафиксирован)
```

**Правило маркеров:** `[NEEDS CLARIFICATION: вопрос]` ставится на каждое место,
где декомпозиция потребовала ассумпции. Переход к plan.md **запрещён**, пока в
spec.md есть хотя бы один маркер: вопросы задаются пользователю, ответы вписываются
в требования, маркер удаляется. Это операционализация Пункта 0 в артефакте.

## plan.md

```markdown
# Plan: [название задачи]

**Spec:** ./spec.md (версия от YYYY-MM-DD) · **Статус:** draft | gates-passed | approved

## Технические решения
| Решение | Обоснование | Из какого требования |
|---------|-------------|----------------------|
| [технология/подход] | [почему] | spec §N |

## Pre-Implementation Gates
<!-- Проверка ДО начала работы. Не прошёл gate → либо упрости план, либо обоснуй в Complexity Tracking -->

### Gate 1 — Surgical scope
- [ ] Каждый шаг плана трассируется к требованию из spec.md
- [ ] Нет шагов «заодно» (рефакторинг/чистка вне запроса)

### Gate 2 — No speculative features
- [ ] Нет обработки edge case'ов, которых не требует спека
- [ ] Нет конфигурируемости там, где работает жёсткое значение
- [ ] Нет абстракций «под будущее расширение», которого нет в спеке

### Gate 3 — Simplicity
- [ ] Минимум новых файлов/модулей (новый файл — только если требование не помещается в существующий)
- [ ] Возможности фреймворка/платформы используются напрямую, без обёрток

## Complexity Tracking
<!-- Каждое отступление от gates — строка здесь. Пусто = отступлений нет -->
| Gate | Отступление | Обоснование |
|------|-------------|-------------|

## Шаги
| # | Что | Результат | Зависит от | Оценка | Spec § |
|---|-----|-----------|-----------|--------|--------|
| 1 | ... | [файл/коммит/проверка] | — | quick | §1 |

## Milestones
Milestone 1: [название] — шаги 1-3. Проверка: [что должно работать]
```

## tasks.md

```markdown
# Tasks: [название задачи]

**Plan:** ./plan.md (версия от YYYY-MM-DD)

| # | Задача | Статус | [P] | Зависит от |
|---|--------|--------|-----|-----------|
| 1 | [императив из плана] | todo / in_progress / done / blocked | [P] если параллелима | — |

## Журнал отклонений
<!-- Новый шаг в процессе работы → строка здесь + регенерация от плана, не молчаливая правка -->
| Дата | Что изменилось | Почему | Затронуло spec/plan? |
|------|---------------|--------|----------------------|
```

## Правила регенерации

| Изменилось | Действие |
|------------|----------|
| Требование в spec.md | Перегенерировать plan.md (затронутые решения и шаги) и tasks.md. Статусы done сохранить для неизменённых задач |
| Шаг в plan.md | Перегенерировать tasks.md. spec.md не трогать |
| Обнаружен новый шаг в работе | Запись в «Журнал отклонений» tasks.md; если шаг меняет scope — сначала spec.md, затем вниз |

Направление всегда сверху вниз: spec → plan → tasks. Правка tasks.md руками в обход плана — анти-паттерн.
