# Retro — Post-Fix Retrospective

**Type:** worker

You just fixed something that didn't work on the first try. Now do an honest retrospective.

**MANDATORY READ:** Load `~/.claude/global-lessons/META.md` — knowledge system rules.

## Step 1: Reconstruct the timeline

Look back through THIS conversation and identify:
- What was the original task/request
- What went wrong (error, wrong approach, failed attempt)
- How many attempts it took to fix
- What was the final working solution

## Step 2: Analyze the chain of reasoning

For EACH attempt, document:
1. **What I thought was the cause** — my hypothesis at that moment
2. **What I did** — the specific change/action
3. **What happened** — the actual result
4. **Was the reasoning correct?** — yes/no and why

Be brutally honest. If I was guessing randomly — say so. If I repeated the same fix — say so.

## Step 3: Why-каскад (root cause через цепочку «почему»)

Метод восходит к Тайити Оно (Toyota Production System). Цель — не остановиться на симптоме, а дойти до **системной** причины (хук, правило, архитектурное решение, отсутствующая инвариант).

### 3.0 Собери проявления (ширина ПО ПРИЗНАКУ, до всякого спуска)

Прежде чем спускаться — найди, где ещё виден ТОТ ЖЕ признак. Не версии причины (они
исполнимы без данных и съедают разбор), а места: поиск по признаку, `dep-index --impact`,
прогон проверки по всему классу однотипных файлов.

- Каждое проявление с адресом: файл:строка, прогон, лог, коммит. Без адреса не считается.
- Нашлось одно — шаг пуст, спускайся как обычно.
- Нашлось несколько — цепочку строй от **2-3 максимально РАЗНЫХ** (разные подсистемы,
  разные авторы, разное время). Схождение цепочек от почти одинаковых случаев ничего не
  подтверждает.

Зачем до спуска, а не после: условие остановки цепочки (3.3, counterfactual) — утверждение
о МНОЖЕСТВЕ путей возникновения. При одном наблюдении проверить его нечем, кроме
рассуждения. Замер 28 августа 2026: один дефект онемил пять стражей, и каждого чинили
отдельным заходом от места, где заметили.

### 3.1 Построй цепочку

Начни с наблюдаемой проблемы. Спроси «почему?» к ответу предыдущего шага. Повторяй пока не дойдёшь до системного уровня.

```
Q0: [что произошло — наблюдаемый симптом]
  Why? → A1: [ближайшая причина]
    Why? → A2: [причина A1]
      Why? → A3: ...
        ...
          → A_final: [системная причина]
```

**Критерий остановки — НЕ глубина 5**, а ответ на вопрос: «это **system-level** причина или ещё симптом?» Системная причина — то, что можно изменить структурно (правило, хук, проверка, абстракция). Если ответ всё ещё «человек ошибся / был невнимателен» — копай глубже.

Глубина обычно 3-7. Если меньше 3 — вероятно остановился рано. Если больше 7 — вероятно ушёл в спекуляции, вернись и проверь эмпирически.

**Спуск идёт двумя линиями, и вторую забывают.** Первая — «почему сломалось здесь» (вдоль
исполнения), она выше. Вторая — **«откуда пришло то, из чего считали»** (вдоль данных):
перечисли ВСЕ входы узла и спроси о каждом, был ли он верен. Ветки с верным входом
отсекаются, с неверным — спуск идёт ТУДА.

```
место, где стало видно
  вход 1 (верен)      → ветка отсечена
  вход 2 (неверен)    → Why? → … → источник A
  вход 3 (неверен)    → Why? → … → источник B
```

Узел, исправно посчитавший то, что ему подали, корнем не является, и признак наблюдаем:
**подай верный вход — симптом исчезнет, хотя узел не менялся.** Источников на этой линии
бывает несколько, и все настоящие. Дно спуска — не число «почему», а владение: последнее
звено внутри того, что меняется своим коммитом.

### 3.2 Разреши ветвление (если есть)

Toyota'вская критика (Minoura, Allspaw): линейная цепочка скрывает множественные причины. Если на каком-то шаге причин **две и больше параллельно** — запиши как ветви:

```
A2: ...
  Why? → A3.a: [причина по линии X]
       → A3.b: [причина по линии Y]
```

Каждая ветвь продолжается отдельно до своего системного уровня. Может оказаться что разные ветви сходятся в общий корень — это сильный сигнал.

**Схождение вверх (если 3.0 дал несколько проявлений).** Ветвление выше — вниз от одного симптома; здесь наоборот: отдельная цепочка от каждого взятого проявления, и сверка, куда они пришли.

```
проявление A → A1 → A2 ─┐
                        ├→ общий корень   ← подтверждён независимо
проявление B → B1 ──────┘
```

- **Сошлись** — подтверждено РОДСТВО проявлений, а не корень. Сошедшееся звено говорит,
  что случаи связаны, и не говорит, что оно сделало симптом ЗДЕСЬ: у узла с несколькими
  входами (сумматор, журнал, отчёт) сходится что угодно, потому что там сходятся входы.
  Корнем звено становится по 3.3 и 3.33, а не фактом схождения.
- **Разошлись** — по умолчанию **корней несколько**, все записываются, у каждого своя
  починка. Подъём к общему узлу допустим только тогда, когда его дробь (3.33) не упала
  против дробей ветвей. Прежняя редакция говорила «поднимайся, пока звено не накроет все
  проявления» — она требовала один накрывающий узел, а ниже точки схождения ни одно звено
  не накрывает всё по построению, и правило выталкивало вверх ровно в момент расхождения.
- **Сошлись формально** — проверь, не общий ли это знаменатель формулировки, а не причины
  (`pattern-subject-of-measurement-mismatch`). Признак подмены: звено объясняет оба случая
  одинаково общо и не предсказывает, где симптом появится третий раз.

### 3.3 Counterfactual test финального звена

Для каждого системного корня (включая ветви) проверь:

> «Если бы A_final не было — симптом не мог бы возникнуть **ни одним путём**?»

Вопрос именно так, а не «произошёл бы этот инцидент»: слабая форма спрашивает про
НАБЛЮДАВШИЙСЯ путь и зеленеет на звене, которое закрывает один путь из нескольких. Сильная
форма — про все пути, потому и требует собранных проявлений (3.0).

Если ответ «всё равно возник бы, потому что есть Z» — Z и есть истинный корень, добавь следующий шаг. Если «нет, ни одним путём» — корень найден.

Эта проверка соответствует правилу `Reproduce first, fix second` — корень эмпирически связан с симптомом, не только логически.

**Названный предел теста.** Он даёт НЕОБХОДИМОСТЬ звена, а не корень, и легчает при
подъёме: «наличие кислорода» проходит его на любом пожаре. Поэтому один он не
останавливает — нужен 3.33. Условие снятия: предел держится, пока достаточность не
проверяется механически; появится проверка «назови НАБОР звеньев, при котором симптом
обязан появиться» с двумя адресами (полный набор с симптомом и набор без кандидата — без
симптома) — необходимости хватит вместе с ней, и 3.33 перестанет быть подпоркой.

### 3.33 Специфичность корня — дробь мест

Единственный тест, который при подъёме **тяжелеет**, и потому единственный встречный
дрейфу вверх. Составь реестр мест: строка — адрес, две колонки — «звено есть» и «симптом
есть». Способ добычи тот же, что в 3.35: `scripts/defect-class-carriers.py`, поиск по
УСТРОЙСТВУ, `scripts/dep-index.py --impact`.

**Дробь** предъявляется числом, а не оценкой: N мест со звеном, M из них с симптомом.
Посчитай ту же дробь на звено выше — шаг, который её роняет, и есть шаг ЗА корень;
остановка на последнем звене до падения.

| Что вышло | Что это значит |
|---|---|
| M = N | корень: все места со звеном больны |
| M < N, второй признак назван | развилка: звено общее, корень — разделитель либо пара |
| M < N, разделитель не назван | разбор НЕ закончен — единственный исход, который нельзя объявлять результатом |

Реестр непостроим (места не перечислимы, чужой код) — так и пишется: **НЕ ИЗМЕРЕНО**, и
зелёным не считается (`case-2026-07-25-null-instrument-reads-as-negative-result`).

Низкая дробь звено не отменяет, а меняет его статус: это не корень, а КЛАСС, и правка под
класс законна только сплошным проходом по всем N местам — не одной починкой с объяснением.

### 3.35 Братья корня (вширь НА УРОВНЕ корня, вбок — до записи case)

Корень подтверждён — теперь спроси не «где ещё виден симптом» (это было 3.0), а **«где ещё
действует корень того же устройства»**: что построено тем же способом и потому откажет так
же, **даже если сейчас зелёное**. Симптома там ещё не видно — потому шаг и не может быть
частью 3.0.

Способ добычи называется, а не подразумевается: `scripts/defect-class-carriers.py` (род
дефекта → носители в дереве), поиск по УСТРОЙСТВУ, `scripts/dep-index.py --impact`.
Каждый брат — с адресом (файл:строка), как в 3.0.

Исход по каждому: чинится тем же корнем **в этой же работе** либо уходит пунктом долга с
адресом. Класс, закрытый в одном механизме и оставленный в соседнем, возвращается тем же
днём (`case-2026-08-29-correction-about-behaviour-outside-analysis-subject`).

Почему до записи case, а не после: Step 5.5 (chain linking) ищет родню в ГРАФЕ ЗНАНИЙ уже
после того, как корень назван и записан, — на определение корня он повлиять не может. Здесь
родня ищется В МИРЕ, и найденные братья входят в сам case как проявления корня.

### 3.4 Зафиксируй пропущенные сигналы

Для каждого звена каскада: какой **сигнал** в тот момент уже указывал на эту причину? (Сообщение об ошибке, лог, поведение, ранее зафиксированное знание.) Что я не прочитал, не запросил, не сопоставил?

Это второй слой обучения — не только «что было причиной», но и «почему я её не увидел раньше».

### 3.5 Маппинг на edges

Каждое звено каскада, которое выходит за рамки одного case'а, становится `caused_by` edge между сущностями знания:

- Симптомы — текущий case
- Промежуточные звенья — могут указывать на существующие case/pattern
- Финальный корень — pattern или principle, если уже формализован

При записи case в Step 4 включи `edges: [caused_by: <parent>]` для каждого звена, где `<parent>` уже есть в базе. Для звеньев, которых ещё нет в базе — кандидаты на новый case/pattern.

## Rules

- Do NOT write vague lessons like "be more careful" or "check more thoroughly"
- Every lesson MUST produce a concrete, actionable rule
- ALWAYS try to connect to existing knowledge (reinforce or contradict)
- If the fix took only 1 attempt — still write the case if the error was non-obvious
- If I was just guessing — admit it and write WHY I couldn't reason properly
- NEVER blame the user, external tools, or "complexity"
- When in doubt about scope — save to global. Redundancy > amnesia
- The goal is not a diary — it's a GROWING INTELLIGENCE that changes behavior

## Definition of Done

- [ ] Timeline reconstructed with all attempts documented
- [ ] Проявления собраны с адресами до спуска; для спуска взяты 2-5 максимально разных (либо названо, что проявление одно)
- [ ] Why-каскад построен до системного уровня (3-7 звеньев — ориентир, не критерий), ветвления разрешены если есть
- [ ] Входы узла перечислены и по каждому сказано, верен ли он (3.1, вторая линия); спуск ушёл в неверные входы, а не встал на месте, где стало видно
- [ ] Если цепочек несколько — схождение сверено: родство подтверждено; при расхождении записаны ВСЕ корни, подъём — только с непадающей дробью
- [ ] Counterfactual test пройден для каждого финального корня
- [ ] Дробь специфичности предъявлена числом (3.33) для каждого корня — либо написано «НЕ ИЗМЕРЕНО» с причиной
- [ ] Братья корня найдены с адресами (3.35): чинятся тем же корнем либо уходят пунктом долга (либо названо, что носитель один)
- [ ] Последствия починки: карта зависимостей корня прогнана; опиравшиеся на прежнее поведение (включая обходные костыли) сняты или записаны пунктом долга
- [ ] Пропущенные сигналы зафиксированы для каждого звена
- [ ] `caused_by` edges добавлены к существующим case/pattern из звеньев каскада
- [ ] Case file saved to `~/.claude/global-lessons/case-*.md`
- [ ] Existing knowledge checked for reinforcement/contradiction
- [ ] Pattern promotion evaluated (2+ similar cases)
- [ ] Chain linking checked (Session Registry, propose edges if domain+trigger match)
- [ ] Modification_history updated (v1.0.8) if pattern/principle was narrowed/branched/deprecated/scope-widened/reinforced-after-challenge; fragile flag recomputed
- [ ] Report shown to user in standard format
