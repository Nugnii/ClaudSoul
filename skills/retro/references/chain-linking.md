# Chain Linking — связывание повторяющихся симптомов (v1.0.7)

**Когда применять:** после создания case на Step 4 /retro, перед промоушеном pattern/principle.

**Зачем каскадно:** один и тот же глубинный корень может проявиться как несколько симптомов в разных сессиях (напр. «медленная загрузка» → «ошибка timeout» → «падение на большом датасете» — разные cases, один корень). Без явных edges они остаются изолированными точками и не складываются в паттерн.

## Алгоритм

### Шаг 1: Извлечь ключевые якоря нового case

Из frontmatter только что созданного `case-YYYY-MM-DD-brief.md`:
- `domain` (список)
- `trigger` (одна строка)
- `stakes` (при наличии)

### Шаг 2: Найти кандидатов в Session Registry

Прочитать `~/.claude/sessions/registry.jsonl` — последние 30 записей:

```bash
tail -30 ~/.claude/sessions/registry.jsonl | jq -r '.knowledge_delta.created[]' | grep -E '^case-' | sort -u
```

Это список case-файлов, созданных в последних сессиях (кроме только что создаваемого).

### Шаг 3: Сверить якоря

Для каждого кандидата `case-X.md`:
1. Прочитать его frontmatter (`awk '/^---$/{n++} n==1; n==2{exit}'`)
2. Сравнить:
   - **domain** — есть пересечение по списку?
   - **trigger** — схож (одинаковая формулировка / синонимы)?
   - **stakes** — совпадают?

Правило совпадения:
- **Strong match:** domain пересекается + trigger синонимичен
- **Weak match:** только domain пересекается
- **No match:** нет пересечения по domain

### Шаг 4: Выбрать тип edge

В зависимости от временной связи и природы совпадения:

| Ситуация | edge |
|----------|------|
| Новый case — последствие предыдущего (прошло < 7 дней, одинаковый trigger, один проект) | `caused_by: [case-X.md]` (у нового) / `led_to: [case-Y.md]` (у старого) |
| Оба случая — похожие инциденты в разных контекстах | `similar_to: [case-X.md]` (взаимно) |
| Новый case уточняет/сужает старый | `specializes: [case-X.md]` |
| Новый case обобщает старый (более общая формулировка) | `generalizes: [case-X.md]` |
| Новый case противоречит выводу старого | `contradicts: [case-X.md]` — + пометить старый для /retro ревизии |

### Шаг 5: Предложить пользователю

**НЕ добавлять edges автоматически.** Это необратимая связь, требующая подтверждения.

Формат предложения (в блоке Step 6 отчёта ретро):

```
🔗 Связанные кейсы (chain linking):
- case-YYYY-MM-DD-X.md — похож по domain=[Y], trigger=[Z]
  Предлагаемая связь: similar_to (или caused_by / specializes / ...)
Подтвердить? (y/n/edit)
```

Если пользователь подтвердил — добавить edge в frontmatter обоих файлов.

### Шаг 6: Эскалация в pattern

Если найдено **3+ strong matches** (один общий корень, но разные поверхностные проявления) — это **сильный сигнал к промоушену в pattern**:

> «Вижу 3+ cases с перекрывающимся domain+trigger: [A, B, C]. Корневая причина может быть общей. Создать pattern/promote?»

Это важнее чем обычный порог «2+ идентичных случая» — т.к. chain означает не повторение, а разные проявления одного механизма.

## Guardrails

- **Не добавлять edges молча.** Всегда подтверждать у пользователя.
- **Не сравнивать с cases из других проектов** без явного разрешения (проверять `project` в Session Registry). Для кросс-доменного переноса — отдельный механизм (hook knowledge-activator уже делает аналогии).
- **Только активные cases.** `status: deprecated` пропустить.
- **Дедуп:** если edge уже существует — пропустить, не дублировать.

## Cost

- Чтение registry.jsonl: 1 tail + jq = минимально
- Per-candidate: 1 файл frontmatter = ~20 строк
- Обычно 0-3 кандидата на ретро, итого ≤100 токенов контекста
- Только при явном match — пользовательский диалог (1 пара сообщений)

Вписывается в token budget Phase 10 (≤430/сессия) легко, т.к. вызывается не каждую сессию, а только при /retro.
