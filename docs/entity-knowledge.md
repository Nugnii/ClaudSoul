# Entity Knowledge — Обучение из внешних источников

> Спецификация Phase 9: второй контур обучения ClaudSoul

---

## 1. Проблема

ClaudSoul учится только из **собственного опыта** (ошибки, успехи, диалоги). Люди учатся иначе — читают книги, изучают документацию, анализируют чужие истории. Это **второй контур обучения**: знания приходят не из действий агента, а из внешнего мира.

### Два контура

```
Контур 1 (v0.1–v0.7):   ДЕЙСТВИЕ → ошибка/успех → case → pattern → principle
                         Агент учится на своём опыте

Контур 2 (v0.9+):       МАТЕРИАЛ → сущности → факты → связи → discovery
                         Агент учится из внешних источников
                                    ↕
                              Domain Graph
                                    ↕
                         Контур 1 (операционный опыт)
```

Контуры не изолированы — они взаимодействуют через Domain Graph и Discovery Engine.

## 2. Источники

| Источник | Формат | Пример |
|----------|--------|--------|
| Документ | PDF, DOCX, TXT, MD | Описание компании, бизнес-план |
| Книга | PDF, EPUB → текст | Учебник по маркетингу, худ. литература |
| Чат-история | JSON, TXT, HTML | Переписка с клиентами, Telegram экспорт |
| Скриншот | PNG, JPG | Скриншот интерфейса, фото документа |
| URL | веб-страница | Статья, новость, документация |
| Голосовая заметка | транскрипт | Запись встречи, голосовое сообщение |

Все источники проходят через единый **Ingestion Pipeline** и преобразуются в сущности, факты и связи.

## 3. Модель данных

### 3.1 Три новых типа знания

Существующие типы (case/pattern/principle) остаются без изменений. Добавляются:

#### Entity (Сущность)

Конкретный объект реального мира: человек, компания, продукт, концепция, событие, место, произведение.

```yaml
---
name: "Иван Петров"
description: "CEO компании TechFlow, ex-Google, Python/Go разработчик"
type: entity
entity_type: person          # person|company|concept|event|place|work|product
status: active

# Атрибуты (ключ-значение, каждый со своим confidence)
attributes:
  role:
    value: "CEO"
    confidence: 4            # из документа + подтверждено в чате
    sources: [company-desc.pdf:p3, chat-2026-03-15:msg42]
  skills:
    - value: "Python"
      level: "junior"        # inferred from behavior
      confidence: 3
      source_type: behavioral   # self-report|behavioral|third-party
      sources: [chat-2026-03-15:msg142, chat-2026-03-20:msg88]
      contradiction:
        stated_level: "senior"
        stated_source: chat-2026-03-10:msg5
        stated_confidence: 1
    - value: "Go"
      level: "senior"
      confidence: 2
      source_type: third-party
      sources: [company-desc.pdf:p7]
  location:
    value: "Москва"
    confidence: 2
    sources: [chat-2026-03-15:msg3]

# Temporal
created: 2026-04-16
last_updated: 2026-04-16
first_seen: company-desc.pdf   # первый источник, где встретилась сущность

# Связи (с другими сущностями и с операционными знаниями)
relations: []                  # см. Relation ниже
edges: []                      # связи с case/pattern/principle
domain: [business, programming]
tags: []
---

Контекст: CEO TechFlow (fintech, основана 2019). В чатах проявляет интерес к Python,
но уровень владения ниже заявленного. Быстро учится — динамика от базовых вопросов
к asyncio за 2 месяца.
```

#### Fact (Факт)

Атрибут сущности или утверждение о мире, не привязанное к конкретной сущности.

```yaml
---
name: "TechFlow — fintech стартап"
description: "Компания TechFlow: fintech, основана 2019, 50+ сотрудников"
type: fact
fact_type: attribute|event|rule|definition
status: active

confidence: 3
sources:
  - id: company-desc.pdf:p1
    type: document
    extracted: 2026-04-16
  - id: chat-2026-03-15:msg22
    type: behavioral
    extracted: 2026-04-16

# Temporal validity (когда факт верен)
valid_from: "2019"           # когда стал верным
valid_until: null            # null = всё ещё верен
temporal_note: ""            # "до ребрендинга", "на момент серии A"

# Привязки
entity_refs: [entity-techflow.md]
domain: [business, fintech]
tags: [startup, fintech, moscow]
---

TechFlow — финтех-стартап, основанный в 2019 году в Москве.
50+ сотрудников. Основной продукт — платёжная платформа для B2B.
```

#### Relation (Связь)

Типизированная связь между двумя сущностями.

```yaml
---
name: "Иван Петров → CEO → TechFlow"
description: "Петров является CEO TechFlow"
type: relation
relation_type: role_in|knows|studied_at|works_at|part_of|created|participated_in|similar_to|contradicts
status: active

confidence: 4
sources: [company-desc.pdf:p3, chat-2026-03-15:msg42]

from_entity: entity-ivan-petrov.md
to_entity: entity-techflow.md
direction: directed              # directed|bidirectional

# Temporal
valid_from: "2021"
valid_until: null

domain: [business]
tags: []
---
```

### 3.2 Confidence из разных источников

Confidence факта зависит не только от количества источников, но и от их **типа**:

| Тип источника | Базовый вес | Пример |
|---------------|-------------|--------|
| **self-report** | 1 | "Я знаю Python" |
| **document** | 2 | Из PDF, описания компании |
| **third-party** | 2 | "Иван у нас ведущий разработчик" |
| **behavioral** | 3 | Вопросы в чате, код, действия |
| **cross-reference** | 4 | Два независимых источника подтверждают |

```
confidence = min(5, sum(source_weights) / count(sources) + bonus)
bonus = +1 если 2+ независимых источника подтверждают
```

### 3.3 Противоречия как сигнал

Когда два источника дают разную информацию — это не ошибка, а **сигнал**:

```
stated_level: senior (self-report, confidence 1)
inferred_level: junior (behavioral, confidence 3)
→ contradiction: true
→ signal: "расхождение между заявленным и реальным уровнем"
```

Механизм тот же, что для `contradicted_count` в операционных знаниях. Противоречие:
- Фиксируется явно (не перезаписывается)
- Повышает "интересность" сущности (аналог intensity)
- Может стать discovery: "Иван преувеличивает свои навыки" → паттерн поведения

### 3.4 Траектория сущности

Факты о сущности меняются во времени. Система отслеживает **динамику**:

```yaml
trajectory:
  - date: 2026-01
    observation: "базовые вопросы по Python"
    source: chat-2026-01-15
  - date: 2026-02
    observation: "вопросы по asyncio"
    source: chat-2026-02-10
  - date: 2026-03
    observation: "помогает другим с FastAPI"
    source: chat-2026-03-22
  inferred_trend: "быстрый рост, ~junior→middle за 3 месяца"
```

Это тот же Trajectory Tracking (Layer 4), но применённый к сущности, а не к мысли собеседника в сессии.

## 4. Ingestion Pipeline

### 4.1 Обзор

```
📥 INPUT          📋 PARSE           🔍 EXTRACT         🧬 INTEGRATE       💡 DISCOVER
─────────         ──────────         ──────────         ──────────         ──────────
PDF/книга    →    Текст/блоки   →   Сущности     →    Domain Graph  →   Паттерны
Чат-история  →    Сообщения     →   Факты        →    Existing KB   →   Противоречия
Скриншот     →    OCR/описание  →   Отношения    →    Cross-ref     →   Неочевидные связи
URL          →    Контент       →   Временные    →    Confidence    →   Рекомендации
                                    метки             scoring
```

### 4.2 Этапы

#### Stage 1: Parse (разбор)

Преобразование входного формата в единую текстовую форму.

| Формат | Метод | Результат |
|--------|-------|-----------|
| PDF | Постраничное чтение (Read tool) | Блоки текста с provenance (файл:страница) |
| Чат-экспорт | JSON/text parsing | Сообщения с автором, временем, контекстом |
| Скриншот | Read tool (мультимодальный) | Описание содержимого |
| URL | WebFetch | HTML → текст |
| Markdown/TXT | Read tool | Текст как есть |

Каждый блок получает **provenance**: `{source_file, page/line/msg_id, extracted_at}`.

#### Stage 2: Extract (извлечение)

Из текста извлекаются:

1. **Именованные сущности** — люди, компании, продукты, места, события
2. **Атрибуты** — роли, характеристики, числа, даты
3. **Отношения** — кто с кем, что к чему, причинно-следственные
4. **Факты** — утверждения о мире, определения, правила
5. **Временные метки** — когда что произошло, периоды валидности

Для чат-историй дополнительно:
- **Поведенческие сигналы** — что человек умеет/знает/хочет (по действиям, не по словам)
- **Коммуникативные паттерны** — стиль, частота, реакции
- **Противоречия** — расхождение между заявленным и наблюдаемым

#### Stage 3: Integrate (интеграция)

Новые сущности и факты интегрируются с существующей базой:

1. **Дедупликация** — "Иван Петров" из документа = "Ivan" из чата? Проверить по контексту
2. **Обогащение** — существующая сущность получает новые атрибуты/источники
3. **Confidence пересчёт** — множественные независимые источники повышают confidence
4. **Domain Graph** — новые домены/узлы добавляются в граф
5. **Cross-reference с операционными знаниями** — "этот человек из чата = actors в case-X"

#### Stage 4: Discover (обнаружение)

Поиск неочевидных связей:

1. **Entity matching** — сущность A (из документа) и сущность B (из чата) — один и тот же человек?
2. **Pattern transfer** — приём из книги по маркетингу применим к текущей задаче клиента?
3. **Contradiction detection** — заявленное ≠ наблюдаемое → сигнал
4. **Cluster analysis** — группы связанных сущностей, которые не были явно связаны

Discovery — не разовая операция. При каждом добавлении новых данных система пересматривает связи.

## 6. Интеграция с Domain Graph

Domain Graph расширяется органически — не нужен отдельный домен "теория". Когда система ингестирует книгу по маркетингу, появляются новые узлы в существующей структуре:

```
domains/
├── _roots.md
├── business.md              # существующий
│   ├── marketing.md         # NEW (из книги по маркетингу)
│   │   ├── positioning.md   # NEW (концепция из книги)
│   │   └── funnel.md        # NEW
│   └── fintech.md           # NEW (из описания компании)
├── programming.md           # существующий
│   ├── python.md            # существующий
│   └── go.md                # существующий
└── people.md                # NEW root domain
    ├── clients.md           # NEW
    └── team.md              # NEW
```

Сущности привязываются к доменам через `domain:` поле. Domain Graph служит **индексом** для быстрого нахождения связей.

## 7. Discovery Engine

### 7.1 Типы discoveries

| Тип | Описание | Пример |
|-----|----------|--------|
| **Identity match** | Одна сущность в разных источниках | "Ivan" из чата = "Иван Петров" из документа |
| **Behavioral inference** | Факт выводится из поведения | Уровень Python из вопросов в чате |
| **Contradiction** | Расхождение между источниками | Заявленный senior ≠ наблюдаемый junior |
| **Hidden connection** | Неочевидная связь через промежуточные сущности | Петров → MIT → Маск (общая alma mater) |
| **Pattern application** | Приём из внешнего источника применим к текущей задаче | Книга о переговорах → стратегия для встречи |
| **Trajectory** | Изменение сущности во времени | Рост навыков, смена роли, эволюция взглядов |

### 7.2 Механизм

Discovery запускается:
1. **При ингесте** — каждый новый источник проверяется против всей базы
2. **При запросе** — пользователь спрашивает о сущности → система ищет все связи
3. **Периодически** — автосканер (cron) пересматривает связи с новыми данными
4. **При совпадении контекста** — knowledge-activator находит entity, релевантный текущей задаче

### 7.3 Confidence для discoveries

Discovery — это гипотеза, не факт. Confidence отражает уверенность:

| Уровень | Confidence | Что значит |
|---------|------------|------------|
| Предположение | 1 | Одно косвенное указание |
| Вероятно | 2 | 2+ косвенных указания |
| Подтверждено | 3 | Прямое указание или 3+ косвенных |
| Верифицировано | 4 | Подтверждено пользователем или из надёжного источника |

## 8. Интеграция с существующими механизмами

### Что переиспользуется

| Механизм | Контур 1 (операционный) | Контур 2 (энциклопедический) |
|----------|------------------------|---------------------------|
| Confidence scoring | Знания об ошибках | Факты о сущностях |
| Contradiction detection | contradicted_count в знаниях | Расхождение между источниками |
| Trajectory tracking | Мысль собеседника (Layer 4) | Развитие сущности во времени |
| Domain Graph | Области знаний агента | Области знаний + сущности мира |
| Cross-domain transfer | Паттерн из проекта A → B | Приём из книги → задача клиента |
| Knowledge-activator | Инжект операционных знаний | Инжект релевантных entity/fact |
| FSRS decay | Устаревание операционных знаний | Устаревание фактов (valid_until) |

### Что новое

| Компонент | Зачем |
|-----------|-------|
| Ingestion Pipeline | Разбор внешних источников |
| Entity/Fact/Relation types | Хранение энциклопедических знаний |
| Behavioral inference | Извлечение фактов из поведения |
| Discovery Engine | Поиск неочевидных связей |
| Source provenance | Отслеживание откуда каждый факт |
| Temporal validity | Когда факт стал/перестал быть верным |

### Мосты между контурами

```
Entity (Контур 2)  ←→  Case (Контур 1)
"Иван Петров"           "При работе с клиентом Петровым
                         важно учитывать что он преувеличивает
                         технический уровень команды"

Fact (Контур 2)    ←→  Pattern (Контур 1)
"Книга: стратегия        "При работе с fintech-клиентами
 positioning для          positioning-подход срабатывает
 fintech-стартапов"       лучше feature-listing"

Discovery (Контур 2) →  Principle (Контур 1)
"Поведенческие данные    "Всегда проверяй заявленный уровень
 надёжнее самоотчёта"     через поведенческие индикаторы,
                          не доверяй самоотчёту"
```

## 9. Скилл /ingest (проектный)

Новый скилл для Ingestion Pipeline:

```
/ingest <источник>              — ингест одного файла/URL
/ingest batch <директория>      — ингест всех файлов в директории
/ingest chat <файл>             — ингест чат-истории (специальный режим)
/ingest status                  — статус обработки источников
```

Дополнительные скиллы:
```
/entity <имя>                   — показать всё что известно о сущности
/discover                       — запустить discovery по всей базе
/discover <сущность>            — найти связи конкретной сущности
```

```
- "Первый в категории побеждает" (fact → candidate for principle)
- "Если не можешь быть первым — создай новую категорию"

💡 Cross-reference с базой знаний:
- TechFlow (entity) — fintech → позиционирование в категории "B2B payments"
  → применим принцип "если не первый — создай категорию"
- pattern-false-obviousness (existing) ←→ "позиционирование ≠ продукт" (из книги)
  → аналогия: то что очевидно нам ≠ то что думает клиент
```

## 11. Ограничения и риски

| Риск | Митигация |
|------|-----------|
| Галлюцинации при extraction | Каждый факт привязан к source + confidence. Без source = confidence 1 |
| Масштаб: тысячи entity | MCP-сервер (Phase 8) с vector search. До этого — Domain Graph как индекс |
| Privacy: чат-истории содержат PII | Sources хранятся локально. Extracted данные — только в global-lessons |
| Ложные discoveries | Discovery = гипотеза (confidence 1-2). Подтверждение пользователем → confidence++ |
| Устаревание фактов | valid_from/valid_until + FSRS decay. Факты без подтверждения за 180 дней → review |
