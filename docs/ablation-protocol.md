# Протокол ablation-замера — попарная оценка эффективности в теневом контроле

> Документ состояния: преregistration-протокол, версия 1.3-prereg (2026-08-08,
> после четырёх раундов внешней рецензии; вердикт: фиксируемый
> preregistration-контракт, концептуальных блокеров нет; правила разработки во
> время фазы согласованы с рецензентом отдельным раундом). Числовые параметры
> §7/§11 подтверждены владельцем и замораживаются первой регистрацией задачи.
> Запуск — после выполнения предпосылок (§15, BACKLOG D64).
> История обсуждения дизайна — CHANGELOG и SESSION.md, сюда не пишется.

## 1. Вопрос

Даёт ли полный ClaudSoul измеримую дельту против чистого Claude Code на автономных
инженерных задачах — и особенно там, где система реально подняла знание до первого
действия. Замер призван заменить измеренным ответом две позиции без данных:
внешнюю оценку «ценны ~20% механизмов» и внутреннюю гипотезу «полезна вся система».
Протокол сознательно НЕ обещает доказать всю архитектуру — он проверяет конкретную
центральную заявку на честно ограниченной популяции задач.

## 2. Дизайн

```
Живой Full — всегда, во всей работе. Только эксплуатационные метрики (§8.2).
Никогда не деградирует: настоящие задачи не решаются без системы.

Случайно выбранная eligible-задача (§5)
        ├── Full shadow    — песочница, снимок текущего ClaudSoul
        └── Vanilla shadow — песочница, чистый Claude Code
                ↓
        объективное парное сравнение (§11)
```

Главный эффект считается **между двумя симметричными тенями** из одного снимка:
обе без собеседника, обе в изоляции — сравнивается система, а не система+среда.
Живой контур в причинную оценку не входит (в нём есть собеседник — самая большая
асимметрия). Плечо Core (минимальное ядро) — следующая фаза после первых 20 пар (§12).

## 3. Целевая популяция (estimand)

**Автономные инженерные задачи, полностью сформулированные до исполнения, с
объективным критерием завершения** (тест проходит / гейт зелёный / DoD выполнен).

Вероятностное сэмплирование снижает выборочное смещение **внутри зарегистрированной
eligible-популяции**; остаточное смещение возможно на этапах регистрации и
классификации eligibility — заявление сильнее этого не делается. Чтобы сжать
субъективность регистрации, вход в журнал механизирован и не зависит от исхода:
**регистрируется каждый принятый верхнеуровневый рабочий запрос — при принятии
цели, до первого tool call.** План, commit, issue или изменение рабочего дерева —
характеристики исхода в журнале, не условие входа: задача, провалившаяся до
первой мутации, из журнала не исчезает.
Внешняя применимость к интерактивным и со-когнитивным задачам не заявляется —
их доля измеряется журналом и выводы на них не переносятся.

## 4. Журнал задач и воронка

Для каждого запроса, зарегистрированного по правилу §3, — запись **до знания
исхода** и **до вычисления сэмплера**: механическая классификация
`substantive / eligible / ineligible` (до исполнения); причина исключения; тип
(bugfix / feature / maintenance); предполагаемая сложность; попала ли в теневой прогон.

Журнал приватен (формулировки реальных задач могут содержать личный контекст);
в публичный снимок уходит воронка числами:
`все запросы → substantive → eligible → выбранные → завершённые пары`
с причинами исключений.

## 5. Сэмплирование

Детерминированное, с commitment-схемой и будущей публичной случайностью:

```
r = HMAC-SHA256( key     = salt_bytes,
                 message = "claudsoul-ablation-v1\0" + task_id_utf8 + "\0"
                           + beacon_output_bytes )
взять в тень ⟺ r mod 4 == 0    # p = 0.25; 4 делит 2^256 — modulo bias нет
SHA256(salt) = 70c5a69d2dd1d33bb91017013bfc56458cc8a2c1228ce050104736f30921ea88
```

HMAC с фиксированным порядком полей и разделителями убирает неоднозначность
конкатенации и даёт domain separation. `beacon_output_bytes` — поле `outputValue`
первого валидного выпуска NIST Randomness Beacon, у которого `timeStamp` позже
момента заморозки предзадачного снимка, `statusCode = 0`, подпись и certificate
проверены; идентификатор выпуска и метка снимка — в журнал. Нет валидного
выпуска — задача остаётся `pending`, другой источник случайности вручную не
подставляется. Владелец знает свою соль, но не будущий beacon — решение сэмплера
непредсказуемо и для него; commitment доказывает, что соль не заменена задним
числом. Соль секретна до
конца замера и хранится вне публичного снимка; после окончания раскрывается, и
любой может пересчитать каждое решение. `task_id` неизменяем и присваивается при
регистрации; eligibility классифицируется **до** вычисления сэмплера.

Суточный бюджет ограничивает скорость исполнения, а не состав выборки: в течение
дня фиксируются дешёвые предзадачные снимки всех eligible-задач; прошедшие
hash-фильтр не отбрасываются, а встают в неизменяемую очередь в порядке
регистрации; исполняется не более одной пары в день, тени запускаются позже
(живому контуру ждать не нужно). Глубина очереди публикуется в воронке.

## 6. Снимки и заморозка

На каждую пару: снимок репозитория задачи, состояния базы знаний и ClaudSoul;
hash кода, конфигурации и базы — в журнал пары. Внутри пары заморозка абсолютная
по построению (обе тени из одного снимка). Оба плеча: одна модель, одна версия
агента, одинаковые разрешения инструментов, одинаковые бюджеты времени и токенов,
параллельный старт (или случайный порядок), один проверяющий скрипт (§9).

Манифест treatment — единственные разрешённые различия плеч:

```
Общее:   модель, версия агента, базовый system prompt, репозиторий,
         инструменты, сеть, бюджеты времени и токенов.
Full:    правила ClaudSoul + хуки + скиллы + MCP + замороженный снимок базы знаний.
Vanilla: ни одного компонента ClaudSoul — без глобальных и проектных правил
         системы, хуков, скиллов, MCP-конфигурации и фрагментов памяти.
```

Перед каждым запуском — автоматический diff окружения против манифеста;
расхождение = `infrastructure_failure` до старта. Injection-токены Full входят
в общий одинаковый token budget — стоимость инъекций оплачивается плечом,
а не только измеряется.

На окно замера замораживается **исполняемая policy: состав хуков, их код, пороги
и правила.** База знаний эволюционирует — это часть адаптивного treatment.
Правки policy копятся и деплоятся после окна. Смена модели Claude или критическое
исправление системы → **разделение фазы**, а не попытка статистически «увидеть»
влияние по hash-ам (hash-штампы документируют дрейф, но не компенсируют его на
двадцати наблюдениях).

**Разработка во время фазы: разрабатывать можно постоянно, активировать —
только между фазами.** Замороженная policy живёт в experimental-теге и всегда
управляет Full shadow; разработка идёт в development-ветке и копится к
следующей фазе; база знаний эволюционирует только через живую работу.
Поведенческие изменения не деплоятся и в **живой** контур во время фазы: живая
работа порождает знания будущих снимков — новая policy косвенно изменила бы
treatment, даже при формально старом shadow-runtime.

Допустимо в фазе: код в отдельной ветке; тесты и документация; проектирование
хуков без подключения; publish-конвейер; будущий Core; накопление изменений к
релизу; естественное пополнение базы знаний живой работой. Недопустимо:
подключать хуки/скиллы; менять activation/retrieval, тексты инъекций,
глобальные правила, пороги/бюджеты/guards; обновлять измеряемую версию MCP;
применять результаты теней как знания; вручную улучшать базу под уже
выбранную задачу.

Результаты теней до конца фазы в базу не подаются: это экспериментальные
данные, не естественный рабочий опыт — иначе будущие пары обучаются на
предыдущих контрольных сравнениях.

Критический дефект: остановить enrollment → зафиксировать завершённые и
ожидающие пары → описать amendment → исправить и проверить систему → новая
фаза с новым hash policy; результаты до и после исправления анализируются
раздельно.

Задачи по разработке самого ClaudSoul: исполняемая Full-policy — в отдельной
**read-only установке** (frozen runtime управляет Full shadow;
mutable-репозиторий — объект задачи, который оба плеча могут менять). Код,
написанный агентом в рабочей копии, не становится исполняемым хуком посреди
того же прогона.

## 7. Стратификация

Два признака (больше — раздробят 20 пар): тип задачи; **знание поднято до действия**.
Второй признак механизирован двумя полями:

- `would_surface_pre_action` — механический, **основная страта**, вычисляется
  **до назначения плеч**: на замороженном task package выполняется
  детерминированный dry-run активатора без запуска агента; результат и
  идентификаторы поднятых знаний (с их состоянием на момент снимка) фиксируются
  в журнале пары как предзадачный признак. Full-плечо получает ровно эту
  инъекцию, Vanilla — нет. Наличие файла в базе недостаточно — признак
  существует, только если dry-run его реально извлёк.
- `knowledge_relevant_blind_review` — слепая оценка релевантности после завершения,
  без знания плеча и исхода; вторичный анализ.

**Центральная заявка (§1) проверяется стратой `would_surface_pre_action = да` —
key secondary estimand (§11): без отдельного подтверждающего решения и поправки
на множественность, публикуется с интервалом как supportive/exploratory.** Если
дельты нет там, где система реально подняла знание, центральная заявка под
вопросом. Порог достаточности страты: минимум **8 завершённых пар** с
`would_surface = да`. Если к закрытию enrollment (§13) их меньше — сбор
продолжается только для этой страты до квоты, но не дольше +4 недель;
добранные задачи входят только в Δ_surface, задним числом в Δ_all не
попадают (§11). Не добрана и тогда — результат по центральной заявке
фиксируется как неразрешающий.

## 8. Метрики

### 8.1 Парные (на теневую пару)

**Primary — одна: успех** (бинарный, по §9). Остальные — secondary/exploratory:

| Метрика | Определение |
|---------|-------------|
| Ошибки по пути | `failed_commands / all_commands` + абсолютные числа (оба публикуются) |
| Стоимость | полные токены задачи, по ВСЕМ запускам, не только успешным (иначе conditioning bias); injection share — механизм-метрика, не показатель качества |
| Время | раздельно: общее / активное время инструментов / генерация / ожидание внешних процессов |

### 8.2 Эксплуатационные (живой контур, пассивно)

Мониторинг, **не доказательство причинного эффекта**: без выключения системы
изменение во времени может объясняться составом задач.

| Метрика | Определение |
|---------|-------------|
| Повторяемость ошибок | `повтор известной ошибки / задачи, где это знание было применимо` |
| Коррекции собеседника | нормировано на 1000 токенов ассистента |
| Навязчивость | доля отклонённых вмешательств; бюджеты gentle/proactive (уже собирается) |
| Разрыв знание→действие | `applicable_not_followed / все применимые активации` |

## 9. Критерий успеха и классификация исходов

Проверяющий скрипт живёт **вне writable-песочниц**, его hash фиксируется до
запусков; изменение тестов, гейта или DoD самим агентом успехом не считается.
Таймаут и потолок токенов фиксированы протоколом (§11); поведение при запросе
уточнения: собеседника нет — исход `blocked`.

Классификация: `success / objective_failure / timeout / blocked /
infrastructure_failure`. Первые четыре механически сводятся к бинарному исходу:
`success → 1`; `objective_failure / timeout / blocked → 0`. `infrastructure_failure` любого плеча аннулирует попытку
**целиком**: оба плеча перезапускаются из исходного снимка — иначе уцелевшее
плечо получает дополнительный шанс на удачную генерацию. Максимум два повтора
на пару, дальше пара исключается как инфраструктурная; все аннулированные
попытки сохраняются в журнале и публикуются в воронке.

## 10. Стохастический шум

Один Full и один Vanilla не отличают эффект системы от случайности конкретной
генерации. Каждая **пятая задача по порядку включения в очередь (§5)** — не по
порядку завершения, чтобы инфраструктурные исключения не меняли будущий график
репликаций — получает второй независимый запуск обоих плеч: +8 запусков на 20
задач, грубая оценка внутриплечевой вариативности. **В primary-анализ входит
первый валидный запуск каждого плеча**; повтор не заменяет его, не усредняется
и не голосует — используется только для оценки flip-rate (доля случаев, где
повтор изменил бинарный исход плеча) и разброса secondary-метрик. Повторять
только дискордантные пары запрещено — это outcome-dependent sampling.

## 11. Анализ

Параметры предрегистрации — в тексте, не «будут определены до старта»
(замораживаются первой регистрацией задачи):

```
Primary estimand: Δ_all = P(success_Full) − P(success_Vanilla)
                  на всех завершённых парах enrollment-набора (§13).
Key secondary:    Δ_surface — то же в страте would_surface = да (§7);
                  без отдельного подтверждающего решения и поправки на
                  множественность; публикуется с интервалом как supportive.

δ  = 0.20 — минимально практически значимый эффект (4 задачи из 20)
CI = 95%, двусторонний, для разности парных долей — метод Agresti–Min

Правило решения — трёхчастная классификация по Δ̂_all и CI:
польза: Δ̂_all ≥ δ  и нижняя граница CI > 0
вред:   Δ̂_all ≤ −δ и верхняя граница CI < 0
иначе:  результат неразрешающий
p-value двустороннего exact McNemar — сопутствующая статистика,
приоритета над правилом решения не имеет.

Бюджет плеча: таймаут 90 минут, потолок 500k токенов — одинаковые для всех
задач и обоих плеч; injection-токены Full входят в этот же потолок (§6).
```

Отсутствие значимости НЕ трактуется как «дельты нет» — на 20 парах ловится только
крупная односторонняя дельта. Публикуются таблица дискордантных пар
`Full+/Vanilla−, Full−/Vanilla+` и доверительный интервал, не только p-value.

Все secondary-метрики (§8.1) — **чисто описательные**: парные разности и
log-ratio `log((x_full + 1) / (x_vanilla + 1))` с медианой и квартилями, без
тестов и без заявлений о значимости. Выбор теста после просмотра распределения —
аналитическая свобода; она закрыта отказом от тестов, а не отложенным выбором.

## 12. Эффект системы ≠ эффект механизмов

Дизайн отвечает на «полный ClaudSoul лучше или хуже Vanilla?» и НЕ отвечает на
«какой именно из десятков хуков создал дельту». По ходу замера механизмы получают только
**эксплуатационные характеристики**: имел ли возможности сработать; срабатывал
или молчал; полезные или ложные вмешательства; измеримая стоимость. Лестница
решений по ним: 0 возможностей → данных недостаточно; много возможностей и 0
полезных срабатываний → кандидат на отключение; редкий, но предотвращающий
большой ущерб guard → оценка через ожидаемый риск; мешает или даёт ложные
срабатывания → кандидат на удаление независимо от редкости.

Причинное утверждение о конкретном механизме требует следующей фазы — `Full ↔
Core` или точечного component ablation: даже если хук сработал в выигравшей
паре, победу мог создать другой компонент.

## 13. Остановка

Enrollment и execution разведены. Enrollment закрывается, когда (а) в
primary-очередь принято 20 задач либо (б) прошло 8 недель с первой принятой —
что раньше. Все задачи, принятые до закрытия, исполняются, даже если анализ
произойдёт позже; выбранные после закрытия в primary-набор не входят.
Календарное закрытие может дать меньше двадцати пар — это принимается: судьба
уже выбранных задач не решается после наблюдения части результатов.
Единственное продление — добор страты `would_surface = да` по правилу §7
(только для Δ_surface, не дольше +4 недель).

## 14. Публикация

Результаты уходят в публичный снимок независимо от направления исхода: воронка,
таблица дискордантных пар, интервалы, страты, hash-реестр версий, метки beacon,
позиции задач в очереди исполнения, аннулированные попытки. Соль сэмплера
раскрывается после окончания — commitment из §5 проверяем любым желающим.

## 15. Предпосылки запуска (не построены — BACKLOG D64)

Запускалка теневых пар (две песочницы из одного снимка: изолированный HOME,
worktree; переиспользуются brain_export и механика снимков publish-конвейера),
журнал задач с механическим правилом входа, детерминированный dry-run активатора
по снимку (§7), environment diff против манифеста treatment (§6), получение
beacon-выпуска (§5), чекер-обвязка вне песочниц, парсер транскриптов пары,
скрипт парного анализа, experimental-тег замороженной policy и отдельная
read-only установка frozen runtime для задач по самому ClaudSoul (§6). Строка в `scripts/measurements.tsv`
появляется вместе с первой завершённой парой — реестр принимает только
исполняемые замеры.

## 16. Ограничения
